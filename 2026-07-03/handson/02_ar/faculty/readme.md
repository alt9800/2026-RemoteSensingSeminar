# ハンズオン② 講師用メモ

## ライブラリ構成（裏取り済み）

- ロケーションベース系コンポーネント（`gps-new-camera` / `gps-new-entity-place`）は
  **使用していない**。座標計算・オブジェクト配置はすべて自前のJavaScriptで行う。AR.jsから
  使っているのは`arjs-device-orientation-controls`（方位によるカメラ回転）のみ。
- `arjs-device-orientation-controls`は`THREEx`というグローバル名前空間を参照する。この
  名前空間は`aframe-ar.js`本体には含まれておらず、別ファイル`ar-threex-location-only.js`
  を**先に**読み込む必要がある。抜けている場合、実行時に`Can't find variable: THREEx`と
  いうエラーが発生し、方位コンポーネントの初期化自体が失敗する。
- AR.js 3.4.7 は A-Frame 1.6.0 を要求する（3.4.4以下はA-Frame 1.0.4）。バージョンの
  組み合わせを崩さない。
- 配信URLは`raw.githack.com/AR-js-org/AR.js/3.4.7/...`。`raw.githubusercontent.com`を
  直接`<script>`に指定するとMIME制限で実行されないため使わない。

## 事前準備

- HTTPS配信（GitHub Pages）。ハンズオン①と同じ。
- 会場の`ube.geojson`が実際の座標を含んでいるか確認する。半径250mの絞り込みがあるため、
  会場から離れた座標のデータだと表示件数が0件になる。0件の場合、HUDに最短距離が表示
  されるので、それが数百m以上であればデータ側の座標が原因と判断できる。

## iOS 対応

- 開始ボタンのタップ内で`DeviceOrientationEvent.requestPermission()`（および
  `DeviceMotionEvent`）を呼んでいる。ページ読み込み時に自動で呼ぶと拒否されるため、
  ゲートを必ず通す。
- 一度許可すると、同一オリジンでは以降ダイアログが出ないことがある。参加者が「許可
  ダイアログが出ない」と言った場合、必ずしも異常ではない。

## 方位のズレと較正パネル

- 方位センサーの値自体は正しくても、AR空間上のオブジェクトが実際の方角と系統的に
  ずれて表示されることがある。AR.jsのリポジトリには、Firefoxでの90度の回転ズレや、
  端末の向き（縦横）切り替え時の誤った回転など、方位・回転処理に関する報告が複数
  存在する。地磁気センサー自体も周辺の金属・鉄筋の影響を受けやすい。
- この種のズレは内部の座標変換に起因するため、アプリケーション側から直接原因を
  修正することは難しい。対処として、画面左下の「方位補正」パネルで、配置済みの
  オブジェクト全体を手動で逆回転させ、見た目のズレを打ち消せるようにしている。
- 較正はその場の見た目に合わせる応急的な手段であり、原因そのものを解消するもの
  ではない。ズレの大きさ・方向が毎回同じかどうかは未確認のため、会場ごとに再調整
  が必要になる可能性がある。

## データの差し替え・変換

- 配布用GeoJSONは、各フィーチャーに`polygon_uuid`（一意な識別子）と`point_lat` /
  `point_lng`（代表点の緯度経度）を持たせる必要がある。`point_lat` / `point_lng`は
  半径絞り込みの距離判定に使うため必須。欠けているフィーチャーは無条件に非表示になる。
- 元データにこの2項目がない場合、頂点座標の単純平均（重心）を計算して付与すればよい。
  `properties.name`がある場合はそのまま残す（ラベル表示時に`polygon_uuid`より優先される）。
- ジオメトリは`Polygon`のみ対応。`Point`のデータはそのままでは扱えない。

## 期待される表示

- 現在地から半径250m以内の筆が、地面レベルの緑色の輪郭線として表示される。立ち上げ
  （押し出し）は行っていないため、平面的な線としてのみ見える。
- ラベルには`name`（あれば）または`polygon_uuid`が表示される。
- 画面右下のミニマップに、現在地のビーコンと、AR側で絞り込んだのと同じ範囲の筆が
  塗りつぶし付きで表示される。タップで全画面表示に切り替わる。
- 端末を回すと、輪郭線が実際の方位の方向に見える（ズレている場合は較正パネルで調整）。

## トラブルシュート

- **カメラは出るが何も表示されない**：GPS未取得（屋内）か、GeoJSONの座標が現在地から
  半径250mより外にある可能性が高い。HUDの「表示: 0件」の横に出る最短距離を確認する。
- **輪郭線は出るが位置・向きが実際とずれる**：方位センサーの系統的なズレの可能性が
  高い。較正パネルで補正する。地磁気センサーの一時的な乱れ（周辺の金属・車両）も
  考えられるため、場所を変えて再確認するのも一つの切り分け方法。
- **`Can't find variable: THREEx`が発生する**：`ar-threex-location-only.js`の読み込み
  漏れ、または`aframe-ar.js`より後に読み込んでいる可能性が高い。
- **iOSで権限ダイアログが出ない**：HTTPSか、タップ内で呼べているかを確認する。
- **ライブラリが読めない**：`raw.githack`のバージョンURLを確認する。当日は事前に
  一度読み込んでおくと、当日の通信環境に左右されにくい。

## 実装の限界（説明ポイント）

- 半径絞り込みは、開始後最初のGPS取得時に一度だけ実行する。参加者が会場内を大きく
  移動した場合、新しく範囲に入った筆は表示されず、圏外に出た筆も表示され続ける。
- 位置情報ベースの精度は数メートル。cm単位が要る用途では、VPS（Immersalの Web SDK
  等）やマーカーベースのARを検討する、という判断につなげる。
- AR.jsの後継として`LocAR.js`が案内されている。iOS向けの修正が多く含まれるとされる。
  今回は資料量と実績からAR.jsを採用しているが、方位のズレが継続的に問題になる場合、
  移行を検討する価値がある。

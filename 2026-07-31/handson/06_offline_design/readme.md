# 06_offline_design：現地調査ツールのオフライン設計（読み物）

実装ではなく設計の話です。現地で使うツールを作る前に、通信前提で足りるかをまず検討してください。オフライン化はコストが高い割に、必要ない場面が多いです。

## 判断基準

| 判断材料 | 通信前提でよい | オフライン設計が必要 |
|----------|---------------|---------------------|
| 調査地の電波 | 市街地・幹線道路沿い | 山間部・谷底 |
| 失敗時の影響 | 後日再訪できる | 再訪困難（船・許可が必要な場所） |
| データ量 | タイル都度取得で足りる | 広域を高ズームで見る必要がある |
| 利用者 | 自分（切り分けできる） | 配布先（トラブル対応できない） |

## オフライン化の手段（コストの低い順）

1. **ブラウザのHTTPキャッシュを温める**：現地に行く前に、対象範囲を必要なズームでなぞっておく。実装不要だが、キャッシュがいつ消えるかは保証されない
2. **Service Worker + Cache Storage**：PWAとしてタイルを明示的に先読み保存する。bbox指定でタイルURL一覧を生成し、`cache.addAll()` で保存するのが基本形。iOS SafariのCache Storageには容量・保持期間の制約がある
3. **タイル同梱＋ローカル配信**：第2回のRaspberry Pi構成。PMTilesファイルとアプリ一式を持ち歩き、ローカルネットワークで配信する。確実だが機材の管理が要る

## 容量の見積り

```
必要容量 ≒ タイル数 × 平均タイルサイズ
```

タイル数はbboxとズーム範囲から機械的に決まります。z14まで市町村1つ分で数百MBになることもあり、全域キャッシュは現実的ではありません。調査対象範囲だけに絞る設計に落ち着くのが普通です。

## PMTilesの範囲切り出し

PMTilesは範囲抽出が用意されています。調査範囲だけの軽いファイルを作って持ち歩く、という運用が素直です。

```sh
pmtiles extract terrain.pmtiles field_area.pmtiles \
  --bbox=131.24,33.96,131.30,34.01
```

Mapterhornが全球データをこの方式で配布しているのは第5回・`02_mapterhorn_compare` で見た通りで、自作データでも同じ道具がそのまま使えます。
